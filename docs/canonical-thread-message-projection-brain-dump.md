# Canonical Thread Message Projection Brain Dump

This is a thinking snapshot, not a spec. It captures where the design conversation landed after Slice 1 got canonical `thread_events` into `packages/lh-context`, and what we think the next layer, projected canonical entities, probably wants to become.

The key shift is that `thread_events` are the durable event substrate, but they are not the shape we want most code, tables, or model-facing logic to think in forever. The next useful layer is a projection into canonical objects: threads, messages, and blocks first, with enough structure to support resume, smoothing, inspection, and later migrations without constantly leaking provider vocabulary into the domain.

## The mood of the design

The north star is effortless high coherence over mechanical explicitness. We want names and shapes that feel crafted, not just faithful to whatever a provider happened to call its JSON fields this quarter.

Some working principles:

- Canonicalize by behavior, not provider vocabulary.
- Add structure only when it earns its keep.
- Use strong types where invalid states matter.
- Preserve provenance as an escape hatch.
- Keep provider and harness weirdness at adapter edges.
- Design by asking what the model, table, or object will be used for.

That last one kept coming up. We do not need a taxonomy because a taxonomy is pretty. We need enough shape for downstream uses: reconstruct a thread, resume with high fidelity, smooth context, inspect what happened, persist queryable rows, and handle future providers without treating every adapter detail as canonical truth.

## Where we are coming from

Slice 1 implemented canonical `thread_events` in `packages/lh-context`. That gives us a durable, append-style event layer. The next question is what the projected canonical entities should look like.

The important correction from real rollout/session inspection was that the repo alone was not enough. Real harness/session files live in multiple places:

- PI files live in `~/.pi` and repo `.pi`.
- Claude Code files live in `~/.claude/projects`.
- Codex files live in `~/.codex/sessions`.

Looking at those changed the mental model. All the harnesses have container messages with typed blocks/content. That argues against treating one atomic event as one message. Projected messages should support message containers plus ordered blocks.

## Current canonical shape

The favored shape is deliberately plain:

- `Thread` is simple, not a union.
- `Thread` contains messages.
- `Message` contains `message_blocks`.
- Likely persistence tables are `threads`, `messages`, and `message_blocks`.

In domain code, the preferred names are `Message` and `MessageBlock`, not `ThreadMessage`, unless exported API ambiguity later forces a disambiguating prefix. Blocks need scoping because "block" alone is too generic. Messages probably do not.

The first implementation slice is intentionally narrower than the full mental model. After source events, the first projected layer is threads, messages, and message blocks. Turns and chunks are still canonical-feeling later derived layers, but they are deferred out of this first slice. Bands are algorithmic compression structures. `thread_views` are generated outputs. Neither should sneak into canonical v1 just because they are useful elsewhere.

The shape is meant to be boring in a good way. A thread has messages. A message has blocks. Actors author messages. Events remain underneath as provenance and replay input. Turns can group messages later.

## Thread creation and identity

This got less mushy after talking through caller behavior.

V1 has explicit thread creation. There is `createThread`, and there is `appendThreadEvents`. They are separate operations.

Important bits:

- `createThread` is not batch.
- `appendThreadEvents` requires an existing thread.
- Missing thread on append is an error.
- Append does not implicitly create a thread.

We intentionally moved away from "append can upsert/create the thread" because mixing explicit create with upsert-on-append felt muddy. It also felt typo-prone: a caller fat-fingers a thread id and suddenly there is a new empty-ish canonical thread instead of a clear failure. Better to make thread existence boring and explicit.

There are two ids in play:

- canonical `threadId`, owned/generated by us
- optional caller/harness `clientThreadId`

`createThread` always creates or returns a canonical `threadId`. If the caller gives a `clientThreadId`, that becomes the natural idempotency key for create. If the caller does not give one, we generate a canonical id and use it as both `threadId` and `clientThreadId`.

Current behavior:

- `createThread({ clientThreadId: "pi-session-123" })` and not found creates a new canonical id, stores the client id, and returns something like `{ created: true, thread: { threadId: "thread_abc", clientThreadId: "pi-session-123" } }`.
- `createThread({ clientThreadId: "pi-session-123" })` and already found returns the existing row with `{ created: false, thread: { threadId: "thread_abc", clientThreadId: "pi-session-123" } }`.
- `createThread({})` creates a fresh canonical id and mirrors it into `clientThreadId`, returning something like `{ created: true, thread: { threadId: "thread_xyz", clientThreadId: "thread_xyz" } }`.

For v1, keep this simple in storage: put `client_thread_id` directly on `threads` with a unique constraint. No separate mapping table yet. A mapping table may become useful later if we need aliases, provider migrations, or multi-origin identity, but that is not the first slice.

One subtle but important API choice: `appendThreadEvents` addresses threads by `clientThreadId`, not canonical `threadId`. Harness/client callers should not need to track our generated canonical id just to append more events. Internally append resolves `clientThreadId` to the canonical thread row, then stores/projections under canonical `thread_id`.

So:

- `appendThreadEvents({ clientThreadId: "pi-session-123", events: [...] })` resolves to canonical thread internally and returns the thread plus per-event results.
- `appendThreadEvents` with a missing/unknown `clientThreadId` returns something like `{ ok: false, error: { code: "thread_not_found", ... } }` and inserts no events.

Exact response envelopes can still move around, but those scenario semantics are settled.

## `thread_created`

New threads get a `thread_created` source event. That event projects the `threads` row.

Returning an existing thread from `createThread` does not write another `thread_created` event. The whole point of using `clientThreadId` as the create natural key is that retrying create can be quiet and idempotent.

`thread_created` does not require a caller-provided `idempotencyKey`. For create, the optional `clientThreadId` is the idempotency/natural key when present. When no client id is present, the generated canonical id becomes both ids and the create is just a normal one-shot creation.

## Append batch semantics

`appendThreadEvents` accepts an array of events, but batch here is transport/convenience. It is not one all-or-nothing mega-transaction.

Current settled shape:

- Process events sequentially.
- Each event gets its own transaction.
- That transaction inserts the source event and its first-level projection rows together.
- Failures are reported synchronously in the append result.
- The result should have per-event success/failure reporting.

Default behavior can stop on first failure unless we intentionally add an option later. The key point is that the caller gets a clear report of what succeeded and failed. No spooky partial batch where the caller has to guess.

## First-level projection boundary

The first-level projection is intentionally local. It looks at the single source event being processed and writes only:

- `threads`
- `messages`
- `message_blocks`

No cross-event assembly here.

That means turns, chunks, tool interaction assembly, smoothing, and `thread_views` all stay in later derived projections. Those layers can read across event/message history. The first projection should not.

A source event may project to zero, one, or many messages/blocks. Do not accidentally lock the model into a 1:1 event-to-message shape, even if most early event types happen to create one message with one block. The container/block model is there because real provider and harness shapes are lumpy.

## Source event strictness

No `unknown_activity` in canonical source events.

That was an escape-hatch idea, but it turns into a junk drawer too easily. Unknown provider shapes should fail at adapter/event validation until we intentionally model them. Raw provider provenance can still exist where appropriate, but canonical events should not invite "shrug, put it over there" behavior.

## Projected ids and table sketch

We are leaning toward deterministic sequential projected ids derived from thread id plus order:

- message id from thread id + message order
- block id from message id + block order

Store numeric order as the real ordering. The string ids are stable handles, but the order columns are what ordering means.

Caveat for future-us: if projection rules change on rebuild, ids can change because message/block order can change. That is acceptable for now, but it is worth remembering before anything external starts treating projected ids as eternal contracts.

Initial table sketch:

- `threads`: `thread_id`, `client_thread_id`, `title`, `created_at`, `updated_at`
- `messages`: `message_id`, `thread_id`, `message_order`, `message_kind`, `actor_json`, `status`, `created_at`, `source_thread_event_id`, `source_event_order`
- `message_blocks`: `block_id`, `message_id`, `thread_id`, `block_order`, `block_kind`, `payload_json`, `source_thread_event_id`

## Message kinds

The message kinds are settled enough for v1:

- `user`
- `assistant`
- `tool_result`
- `system`

There is no `summary` message kind for now. Turns and chunks already carry summaries, bands are algorithmic compression structures, and `thread_views` are generated outputs rather than canonical v1 entities. A summary message would look tidy, but right now it risks mixing generated/context-management artifacts into the conversation substrate.

There is also no `unknown`, `custom`, or provider-extension message kind in v1. Same current bias as before: let new types emerge when integrating providers instead of baking in an escape hatch that every caller then has to defensively handle. Provenance gives us a way back to the raw shape if something surprising appears.

## System messages

`messageKind: "system"` is for entries that materially affect context, resume, or interpretation but are not ordinary user, assistant, or tool-result content.

The current `systemKind` set:

- `session`
- `instruction`
- `configuration`
- `lifecycle`
- `runtime_error`
- `context_change`
- `attachment`

Provider grounding that made this feel real:

- PI has session/model-change/thinking-level-change style records.
- Codex has session metadata, turn context, instructions, errors, and context-compacted records.
- Claude has system records, stop hooks, API errors, and context-affecting attachments.

Important caveat: not every provider bookkeeping row becomes a system message. A lot of rows should stay as events, metadata, or provenance only. The system message threshold is that it affects the reconstructed context or how a later reader/model should interpret the thread.

## Message status

Messages get a small status enum because it earns its keep:

- `complete`
- `incomplete`
- `aborted`
- `error`

Default to `complete`. Set a non-complete status only when there is evidence, not vibes.

Why this seems worth carrying:

- PI has assistant `stopReason` values like `stop`, `toolUse`, `error`, and `aborted`.
- Claude can have `stop_reason: null`, `interruptedMessageId`, API errors, and `tool_result` payloads with `is_error`.
- Codex has task completion, turn abort/error signals, and tool statuses.

Tool-use continuation is still a complete assistant message. It is complete as a message container, just not turn-final. A tool result error should make the `tool_result` message status `error`.

## Blocks

The currently favored block kinds are:

- `text`
- `thinking`
- `tool_call`
- `tool_result`
- `image`
- `file`

Tool calls are likely blocks inside assistant messages. Tool results are top-level messages, and may also use `tool_result` blocks inside those messages. That looks a little redundant on paper, but behaviorally it fits the harnesses: a tool result is a message in the conversation stream, and its payload can still be structured as one or more blocks.

Tool call/result correlation should use `toolCallId` only for now. There is no enforced relationship yet. That can wait until a real consumer needs stronger guarantees, because tool plumbing across harnesses is exactly where false precision gets expensive.

Images and files are still an open v1 decision. They are in the favored block list because the model is clearly multi-modal enough to need containers for them, but the exact persistence shape and migration scope are not settled.

## Thinking blocks

Thinking is not audit-grade. That was an important line to draw.

It exists for high fidelity resume and smoothing, not for proving what the model "really thought." Some providers expose summaries, encrypted payloads, redacted payloads, or reasoning-ish fields, but we should not overclaim what those mean.

Favored thinking kinds:

- `reasoning`
- `reasoning_summary`
- `encrypted_reasoning`

Current mappings:

- Anthropic `redacted_thinking` maps to `encrypted_reasoning`.
- OpenAI `encrypted_content` maps to `encrypted_reasoning`.

If encrypted reasoning and a summary arrive together, they become separate sibling thinking blocks. No grouping unless a real need appears.

Smoothing should use `reasoning` first, then `reasoning_summary`, and never `encrypted_reasoning`. Chunks ignore thinking for now.

This keeps thinking useful without turning it into a magical special case. It is just a block family with a few careful rules around downstream use.

## Actors

Projected messages require an actor.

Input events and adapters can be messy or defaulted. The projector is where defaults get resolved:

- `user-default`
- `assistant-default`
- tool default
- system/runtime default

This supports the normal single-user/single-assistant case without giving up on future multi-user or multi-assistant threads. The domain object gets coherence; the adapter layer absorbs the weirdness.

## Turns

Turns still feel like maintained canonical groupings over messages, just not in the first implementation slice.

Future/later derived layer thinking:

A turn starts with a user prompt and ends after the assistant final/terminal completion when known, otherwise before the next user prompt.

We should avoid an always-open latest turn. That shape is tempting because it seems convenient, but it makes the current tail ambiguous and pushes lifecycle uncertainty into every consumer.

Possible turn fields when this layer exists:

- `status`: probably `open` or `complete`
- start message order
- end message order

No `closeReason` unless it earns its keep. A status plus boundary orders may be enough, but this is deliberately later-layer thinking now, not a v1 schema promise.

## Assistant finality and turn closure

One of the useful discoveries from inspecting harness files is that assistant "finality" is not one universal boolean.

PI persisted assistant `stopReason` values:

- `stop` means successful final answer.
- `toolUse` means continuation.
- `error` and `aborted` are terminal but not final answers.

PI `turn_end` is a lifecycle fallback.

Codex final assistant output is a `response_item` message with phase `final_answer`, but `task_complete` is the durable turn closure.

Claude Code has assistant `stop_reason` values where:

- `end_turn` means the model is done.
- `tool_use` means continuation.
- `stop_sequence` is abnormal.

For Claude Code, system `turn_duration` is the strongest closure marker, and stop hooks can continue after `end_turn`.

The conclusion: do not use an `isFinal` boolean. `messageStatus` and `stopReason` are useful message-level details, but turn closure should be maintained separately once turns exist, and should use lifecycle closure events when available.

This is the kind of thing that sounds like a detail until it decides whether resume faithfully lands in the right place.

## Thread views, bands, and chunks

The current bias is that `thread_views` are generated outputs, not canonical v1.

Bands are algorithmic compression structures. They should not masquerade as messages.

Chunks carry summaries, but chunks ignore thinking for now. That may change later, especially if resume quality wants a richer representation of reasoning summaries. For this slice, chunks are also deferred. The first projection does not need to solve them.

## Why this shape feels right

The real harnesses nudged us toward containers plus blocks. The naming conversation nudged us toward `Message`/`MessageBlock` rather than provider-shaped nouns. The lifecycle inspection nudged us away from `isFinal` and toward message status now, with a separate maintained turn projection later.

The pattern underneath all of this is: make the canonical layer easy to think with, and keep the raw event/provider detail recoverable but not dominant.

The raw event says what happened. The projection says what we currently believe the conversation is.

## Working notes for this branch

This branch is for exploring a narrower-but-important infrastructure move before the projection hardens: migrate the new source-event path in `packages/lh-context` `thread_events` from direct `better-sqlite3` usage to Effect SQL with the SQLite provider.

This is not about the old existing steward SQLite path. Leave that alone.

Why this feels worth doing now:

- The repo is moving SDK-first, and this keeps the new context substrate aligned with that direction.
- Provider agnosticism probably matters later: SQLite now, maybe Postgres/Aurora later.
- Effect SQL gives us a more coherent Effect-shaped home for schema, errors, SQL, transactions, and observability.
- If we wait until after messages/message_blocks are built, adopting Effect SQL later means porting transaction, connection, and migration boundaries after more code depends on them.

Durable queue/workflow research landed in a slightly split place. Effect PubSub alone is in-memory, so it is not the answer for durable projection or derived-layer work. But there are real durable candidates around the Effect ecosystem and nearby SQLite world:

- `@effect/sql` `SqlPersistedQueue`
- Honker SQLite durable queue/pubsub
- a minimal transactional outbox
- `@effect/workflow`/Reflow later, especially for multi-step smart compression

The first-level projection still probably wants to be synchronous and transactional. `thread_events` -> `threads`/`messages`/`message_blocks` should commit together because it is cheap, foundational, and immediately readable.

Durable queues and workflows matter more for later derived layers: turns, chunks, token accounting, smart compression, and thread views. Those are the places where retryable async work and multi-step orchestration start earning their keep.

Current branch plan:

1. Refactor `thread_events` storage to Effect SQL with the SQLite provider.
2. Get the existing/new tests passing against that storage.
3. Build the `messages`/`message_blocks` projection on top of the new SQL boundary.
4. Later, spike `SqlPersistedQueue` for turns/chunks rather than forcing it into this first projection.

## Current open decisions

Still open:

- Exact payload schemas for messages/blocks/system details.
- Exact result envelope shapes for `createThread` and `appendThreadEvents`, especially the per-event append result structure.
- Persistence implementation details for the first projection.
- Projector replay/rebuild/update behavior, including how much projected-id churn is acceptable across rule changes.
- Whether `image` and `file` blocks make v1.
- Migration scope.
- How much actor structure to persist immediately versus synthesize during projection.
- How aggressively to expose provenance on every projected row.

Turns and chunks move to the later-derived-layer pile. There are still important decisions there, especially around turn closure and summary/chunk behavior, but they are no longer blocking canonical v1.

The next good work is probably to draft the smallest event-derived messages-plus-blocks projection schema that can survive real PI, Codex, and Claude Code session examples, then test it against those harness shapes before polishing any names into permanence.
